# Main User Study (Controlled Pilot Study) — Implementation Reference

**Canonical protocol: `final_report_2026/method/method.tex`** (sections "Controlled Pilot Study
Design" onward). This file is the implementation-oriented summary for Claude Code; if it ever
disagrees with method.tex, method.tex wins and this file should be updated.

Last aligned with method.tex: 2026-07-09. The earlier version of this document (X/Y/Z sequence
sets, repeated identical trials, black-key Level 3, audible keyboard, blocked Latin-square
condition orders) is superseded — the design has since been revised substantially.

Old experiments under `individual_project_2026/experiments/` (attachment verification, LRA/ERM
reaction) are pilot/validation work, not the main protocol.

## Study in one paragraph

A within-subject controlled pilot feasibility study, N = 10. Every participant completes 27
formal trials (3 feedback conditions × 3 difficulty levels × 3 unique sequences), each trial a
30-event single-key cue-response sequence, for 810 target keypress events per participant. It
estimates preliminary directionality only — not confirmatory inference.

## Research questions

- **RQ1** — direction of difference when explicit finger guidance (B, C) is added to key-only
  guidance (A) in complete key-finger action performance.
- **RQ2 (main)** — direction of difference between visual (B) and nail-mounted vibrotactile (C)
  finger guidance under matched motor-sequence difficulty.

## Conditions

The target key is always backlit. Each cue event has exactly one target key and one target
finger. **Actuators are worn in every condition** — attached before the first practice trial,
removed after the last formal trial — so the manipulated variable is the activation state, not
device presence.

| Condition | Key cue | Finger cue | Actuators |
| --- | --- | --- | --- |
| A — key-only | backlight | none | worn, inactive |
| B — visual finger cue | backlight | screen cue (e.g. R2 / highlighted finger) | worn, inactive |
| C — vibrotactile finger cue | backlight | vibration on target finger | worn, active per cue |

Implementation rules: A shows no finger information anywhere; B shows it visually but never
vibrates; C vibrates but shows no visual finger information.

**Auditory control: the session is silent.** Keyboard local speaker, host synthesiser, and any
software instrument are muted; no headphones. MIDI events are still logged.

## Stimuli

Generated by `python-code/experiment_sequence_wizard.py` (algorithm:
`python-code/SEQUENCE_GENERATOR_ALGORITHM.md`), not selected from real music:

- Fixed **T = 30 single-key events** per sequence; one hand/finger/note per event; no chords.
- **Both hands across every sequence** (bimanual at sequence level); left/right event counts
  balanced; difficulty never changes hand usage — all levels are bimanual.
- **White keys only**, on the calibrated profile's own MIDI range (planned pilot profile:
  MIDI 48–72). No black keys at any level (unlike the earlier draft design).
- Difficulty levels **α / β / γ** defined by measurable constraints on
  **D = (C_m, C_s, C_c)** (motor cost, sequence complexity, bimanual coordination) — see the
  algorithm doc for the constraint table. No subjective difficulty labels.
- Per level, the generator builds a **matched pool** (default 9 sequences, pairwise matched on
  H_norm, d̄m/S, A_h, B_h, O_LR) and validates the three pools for monotonic difficulty before
  locking. Generation is **seeded**; each saved sequence's `meta.json` records seed, count, and
  note bounds, so the locked pools are exactly reproducible.
- Saved under `python-code/data/sequence/<name>/` in the standard song layout, loadable by the
  quiz tools directly.

## Trial structure and randomisation

- 3 conditions × 3 levels × **3 unique sequences per condition–level cell** = 27 trials. The
  three trials in a cell are *different* sequences sampled from the level pool — **not** repeats
  of one sequence (trial index = exposure to unique material, not repetition learning).
- The full 27-trial list is **randomised and interleaved** (conditions and levels mixed, not
  nested blocks). Across the N = 10 cohort, randomisation is stratified to balance starting
  condition, starting level, and condition-transition frequencies. Schedule, seed, actual orders,
  sequence IDs, and trial positions are all logged.
- Session flow: consent/demographics → actuator attachment + comfort check → 2–3 min
  familiarisation (demo cues not reused in formal pools) → non-recorded practice → 27 formal
  trials with **mandatory 2 min rests after trials 9 and 18** (cues cleared, actuators inactive
  but attached) → final comfort check, removal. Participant-requested extra rests allowed and
  logged.

## Cue event flow

1. Backlight the single target key; show/trigger the condition's finger cue; record cue onset.
2. Participant presses the cued key once with the indicated finger (when provided).
3. Event completes on the expected MIDI note-on or when the response window (5 s) expires.
4. Clear cues, record release where available, fixed **750 ms** blank, next cue.

No fixed note-hold duration; no rhythm — reaction time reflects cue-guided action selection.

## Haptic cue design

One fixed design: finger identity encoded by actuator location only, no pulse patterns.
Default `continuous_until_response`, timeout 5 s, constant internal amplitude (logged
automatically). Fixed-duration (e.g. 500 ms) is the fallback if pilot testing shows discomfort —
any change must be recorded and treated consistently. Do not expose pulse/amplitude controls in
the study GUI. LRA actuators (selected over ERM by the earlier validation:
`experiments/human_reaction_experiment/analysis_output/analysis_report.md`); actuator type is not
a study factor.

## Data logging (minimum set, per method.tex)

Participant ID, session time, keyboard profile, randomisation seed, familiarisation/practice
completed flags, overall trial position, condition, level, sequence pool, sequence ID,
within-cell trial index, event index, START_NOTE/END_NOTE, target key_id / MIDI note / finger /
hand, previous target hand + same-hand-vs-switch flag, all components of C_m/C_s/C_c,
audio-muted status, actuator-attached and actuator-active status, cue onset / LED onset / visual
cue onset / haptic command times, haptic mode + amplitude, actual MIDI note, keypress time,
release time, timeout status, false-start count, scheduled-rest index and rest start/end/duration,
any participant-requested rests.

Scoring: *note correct* (MIDI), *finger correct* (offline camera analysis), *action correct* =
both. Ambiguous finger assignments are excluded from primary finger accuracy and reported as an
ambiguity rate (plus a conservative ambiguous-as-incorrect sensitivity analysis).

## Outcome measures

Per participant × condition × level × sequence × trial index: note accuracy, finger accuracy,
action accuracy, reaction time (correct notes / correct actions), error rate per condition,
timeout rate, ambiguous-assignment rate, hand-transition effects (same-hand vs switch), and
trial-order trend across the three unique sequences. Analysis is exploratory/pilot: within-subject
summaries, paired contrasts, directionality; principal comparison B vs C.

## Subjective questionnaire

After the full schedule: per-condition 5-point Likert blocks (cue clarity, ease, comfort,
confidence, preference; wording adapted for A), one whole-session item on wearing the actuators
throughout, and a final preference question with reasons.
